# Rebalancer 4.3.1 – release notes

Packages: `Rebalancer.Core`, `Rebalancer.SqlServer`, `Rebalancer.Redis`, `Rebalancer.ZooKeeper`,
`Rebalancer.Extensions.DependencyInjection`, `Rebalancer.Extensions.Diagnostics.HealthChecks` (all 4.3.1).

Change record: [CR-0011](../change-records/CR-0011-release-4-3-1.md). No API, configuration or data format change;
any upgrade order works. One fix for SQL Server and Redis hosts.

## Fix: StopAsync now raises OnUnassignment on SQL Server and Redis

`RebalancerClient.StopAsync` is documented to invoke the unassignment handlers before it returns, and the ZooKeeper
client always did. A SQL Server or Redis client did not: on a clean stop it deleted its client record but never raised
`OnUnassignment`. A host that stops its handlers in `OnUnassignment` kept processing its resources after `StopAsync`
returned, while the coordinator gave them to another node, so two nodes could process the same resource. Now the
client raises `OnUnassignment` once its tasks have stopped and before its record is deleted, so the coordinator
reassigns only resources nobody processes. Nothing is raised for a client that was never assigned.

**Check your stop logic:** a host that stops its handlers both in `OnUnassignment` and after `StopAsync` now runs
that logic twice; it should tolerate that.

## Tests

- Network faults checked at the level of what nodes actually process (no resource processed by two nodes at once):
  nodes coming and going over a slow, lossy link (SQL Server, Redis, ZooKeeper); a node partitioned from or crashed
  out of a ZooKeeper ensemble; the loss of a ZooKeeper follower, the leader, or the quorum.
- A clean stop raises `OnUnassignment` before `StopAsync` returns (SQL Server, Redis).
