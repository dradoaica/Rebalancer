# Rebalancer 2.1.0 – release notes

Packages: `Rebalancer.Core`, `Rebalancer.SqlServer`, `Rebalancer.Redis`, `Rebalancer.ZooKeeper`,
`Rebalancer.Extensions.DependencyInjection` (all 2.1.0).

Change record: [CR-0001](../change-records/CR-0001-coordination-safety-and-provider-ownership.md)
(Approved, with Amendment 1).

## Upgrade notes – read first

- **Redis: upgrade every node of a resource group at once.** Stop all nodes, deploy 2.1.0, start them again. Lease
  and keep-alive times now come from the Redis server clock, and updates are compare-and-set. A group that mixes 2.0.x
  and 2.1.0 nodes would compare times from two clocks and could lose updates. SQL Server and ZooKeeper groups can be
  upgraded node by node.
- **No data migration.** The SQL Server schema and the Redis key/JSON format are unchanged, so rollback is
  redeploying 2.0.3 (Redis groups again all at once).

## Behavior changes (potentially breaking)

Every public signature from 2.0.3 still exists, but these behaviors changed:

1. **`RebalancerClient` owns its provider** ([ADR 0006](../adrs/0006-provider-resource-ownership-and-zookeeper-acl.md)).
   `Dispose()` now disposes a provider that implements `IDisposable`, also after `StopAsync`. `RedisProvider` now
   implements `IDisposable` and closes its Redis connection. **Use one provider instance per client.** The DI
   registrations already do.
2. **`GetAssignedResources()` no longer blocks on SQL Server and Redis**
   ([ADR 0007](../adrs/0007-non-blocking-get-assigned-resources.md)). While assignment is pending it returns
   `PendingAssignment` with no resources, as documented and as ZooKeeper already did. Previously it could block a
   thread forever. To wait, use the providers' `GetAssignedResources(CancellationToken)`.
3. **`StackExchange.Redis.DataTypes` is no longer a dependency of `Rebalancer.Redis`**
   ([ADR 0008](../adrs/0008-replace-redis-datatypes-with-direct-newtonsoft-json.md)). If your code uses
   `RedisDictionary` / `RedisList`, reference that package yourself.
4. **A conflicting `Providers.Register` call now throws `ProviderException`**
   ([ADR 0009](../adrs/0009-reject-conflicting-provider-registrations.md)). A second registration with a *different*
   factory used to be silently ignored. Registering the same factory again is still a no-op. To use several providers
   in one process, use `new RebalancerClient(provider)` or the DI extensions.

## Fixes

### Assignment safety

- **A demoted SQL Server / Redis coordinator kept processing its resources**
  ([problem record](../problem-records/PRB-0001-demoted-coordinator-keeps-resources.md)). After losing its
  lease (for example after a long GC pause), the old coordinator was not stopped by the new coordinator's barrier, so
  two nodes could process the same resource. The coordinator now records its own `Waiting` / `Active` status and
  clears its local state when it stops. While rebalancing, it reports `PendingAssignment` like followers.
- **Redis leases and client updates are atomic.** Acquire, renew and relinquish are compare-and-set on the lease
  record, evaluated with Redis server time. A failure no longer clears a lease that may belong to another, healthy
  coordinator. Starting or stopping several clients is all-or-nothing and guarded by fencing tokens. Previously a
  fencing-token violation was ignored.
- **SQL Server: starting clients is one transaction**, so either all clients are granted their resources or none.
  Lease reads use `UPDATE … OUTPUT` in the same serializable transaction.

### Reliability

- SQL Server: connections are disposed on failed opens, and transactions and commands are disposed (an uncommitted
  transaction rolls back).
- ZooKeeper:
    - Waits and backoffs honor cancellation, so stopping is no longer delayed by restart and connection-loss waits.
    - A new session no longer reports "connected" too early, based on the previous session's state.
    - An expired session is detected from the watcher event.
    - A missing epoch znode or an empty status znode is handled instead of throwing a `NullReferenceException`.
- ZooKeeper GlobalBarrier: a failed verify phase was reported with the assign phase's result.
- ZooKeeper: a rejected start no longer leaves the resource manager locked, which blocked later stops.
- ZooKeeper: `ZooKeeperProvider` falls back to a no-op logger when given `null`, like the other providers.
  Previously the first log call threw.
- `RebalancerClient.Dispose()` no longer throws when the provider faulted.
- Redis: reading resources is asynchronous; it no longer blocks a thread pool thread.
- Logging: several messages passed the exception text as the client id; fixed.

## New features

- **ZooKeeper ACLs (opt-in)** ([ADR 0006](../adrs/0006-provider-resource-ownership-and-zookeeper-acl.md)).
  `ZooKeeperProvider`, `ZooKeeperService` and `AddRebalancerZooKeeper` have overloads that take an ACL and an auth
  scheme (e.g. `digest`). With credentials and no explicit ACL, znodes are created with `CREATOR_ALL_ACL`. The default
  stays
  `OPEN_ACL_UNSAFE`. See the operator notes in `src/Rebalancer.ZooKeeper/README.md`: every node of a group must use the
  same credentials, and the `resources` znode you create yourself holds the assignment table.
- **Warning for open znodes** ([ADR 0010](../adrs/0010-warn-on-open-operator-znodes-when-acls-are-configured.md)).
  With credentials configured, the ZooKeeper provider logs a warning for the group znode and the `resources` znode if
  anyone can change them, or if their ACL cannot be read. Configure a logger to see it.

## Security

- `Rebalancer.Redis` no longer pulls `Newtonsoft.Json` 12.0.1 (advisory GHSA-5crp-9r3c-p9vr); it references 13.0.3.
- Threat models: [TM-0001 ZooKeeper](../threat-models/TM-0001-zookeeper-coordination-and-acl.md),
  [TM-0002 SQL Server](../threat-models/TM-0002-sql-server-coordination.md),
  [TM-0003 Redis](../threat-models/TM-0003-redis-coordination.md) (all Accepted). They list the deployment controls
  (least-privilege SQL login, Redis authentication and TLS, ZooKeeper credentials) and the accepted residual risks.

## Deprecation notice

- **ZooKeeper without credentials will require an explicit opt-out in 3.0**
  ([ADR 0011](../adrs/0011-zookeeper-acls-by-default-in-next-major-version.md)). A later 2.x release will mark the
  entry points without credentials `[Obsolete]`. Nothing changes in 2.1.0.

## Tests and tooling

- New unit tests cover:
    - coordinator demotion (both backends);
    - Redis lease decisions;
    - the client lifecycle;
    - non-blocking `GetAssignedResources()`;
    - provider registration;
    - ZooKeeper ACL API compatibility.
- The ZooKeeper integration tests now really run both barrier modes. They used to run every test with the first
  test's provider ([problem record](../problem-records/PRB-0002-zookeeper-tests-ignored-their-provider.md)).
- New ZooKeeper ACL integration tests.
- The randomised ZooKeeper tests no longer write to a hardcoded path; `REBALANCER_RANDOMISED_TEST_MAX_MINUTES` caps
  their
  run time for a smoke run.
- The Redis / SQL Server safety tests also check that the resource is assigned at all.
- The README documents a local 3-node ZooKeeper cluster for the integration tests.
- Verified before release: unit tests 27/27; Redis and SQL Server integration 2/2; ZooKeeper single-client,
  multi-client and ACL 22/22; randomised ZooKeeper smoke run (2-minute cap) 6/13 run, all passed.

## Known issues

- SQL Server and Redis never delete terminated client records; on Redis every node reads all of them on every
  heartbeat. Clean up old `Terminated` entries periodically (TM-0002, TM-0003).
- The example and test projects report advisories for `System.Security.Cryptography.Pkcs` 9.0.18; the published
  libraries are not affected.
