# Rebalancer 4.3.0 – release notes

Packages: `Rebalancer.Core`, `Rebalancer.SqlServer`, `Rebalancer.Redis`, `Rebalancer.ZooKeeper`,
`Rebalancer.Extensions.DependencyInjection`, `Rebalancer.Extensions.Diagnostics.HealthChecks` (all 4.3.0).

Change record: [CR-0010](../change-records/CR-0010-release-4-3-0.md). No public API, configuration or data format
change. Four fixes to the coordination protocols, found by model checking them in TLA+ ([
`docs/tlaplus/`](../tlaplus/README.md)); two of them could let two nodes process the same resource. One behavior
change for ZooKeeper hosts: see "ZooKeeper: handlers stop when the connection is lost".

**Upgrade every node of a group.** The fixes protect a group fully only once all its nodes run 4.3.0; mixed versions
work, with the old behavior on the old nodes.

## Fix: a recovered SQL Server or Redis follower was never assigned again

[PRB-0005](../problem-records/PRB-0005-recovered-follower-never-reassigned.md). Affects hosts that set
`AutoRecoveryOnError`.

A follower that hit an error (for example a store timeout) restarted, but its client record stayed `Terminated`, which
no coordinator includes. It was never given resources again until its process restarted, and it kept reporting its old
assignment although its handlers had stopped. Now the record goes back to the state a new client registers with, the
coordinator assigns the client again, and `GetCurrentState()` reports `PendingAssignment` until it does. The health
check reported such a follower `Unhealthy`; that clears once it is assigned again.

## Fix: a resumed SQL Server or Redis coordinator could keep processing reassigned resources

[ADR-0026](../adrs/0026-coordinator-acts-only-under-a-valid-lease.md). Needs a node to stall longer than the lease
expiry (GC pause, VM freeze), the condition 3.1.0's notes warn about.

A coordinator that stalled past its lease expiry and resumed did not check its lease before acting: it could finish a
rebalancing, or keep its own resources, while another node already held them, for longer than the one tick 3.1.0
documents. After two such stalls, a node that became coordinator again could keep processing a reassigned resource
indefinitely. Now each coordinator heartbeat and every coordinator write checks that the lease still names it with its
fencing token; a coordinator that is fenced out stops its handlers at once, and each new tenure starts with a
rebalance. On SQL Server the coordinator's existing fencing check also works now (it never fired there).

The window that remains is the one 3.1.0 documents: a resumed node can run its handlers until its first tick
([ADR-0021](../adrs/0021-assignment-generation-for-resource-handlers.md)). Keep the lease expiry well above the longest
pause a node can have.

## Fix: a ZooKeeper client could delete another client's resource barrier

[ADR-0027](../adrs/0027-zookeeper-client-deletes-only-its-own-resource-barriers.md). Affects
`RebalancingMode.ResourceBarrier`. Needs no failure.

When several assignment changes followed each other quickly (a client joining and a resource being removed), a client
waiting for a barrier could be cancelled and then delete the barrier that another client still held; a third client
could then start the same resource. After a lost session, a client could also delete barriers of resources it had run
in the old session. Now a client deletes only barriers that hold its own client id, and forgets its resources after a
lost session.

## ZooKeeper: handlers stop when the connection is lost (behavior change)

[ADR-0028](../adrs/0028-zookeeper-client-stops-handlers-when-disconnected.md). Both rebalancing modes.

A disconnected client kept its handlers running until its own timer gave up the session, at about the time ZooKeeper
could expire that session and let another client start the same resources. Now a client stops its handlers as soon as
it sees the connection drop, and keeps its session and assignment; no handler starts while it is disconnected. When the
connection comes back with the same session, a follower responds to the current assignment again and the coordinator
restarts its own share.

What hosts see:

- Stop and start callbacks (`OnUnassignment`, `OnAssignment`) on a disconnection that lasts long enough for ZooKeeper's
  client to report it (about two thirds of the session timeout), and `PendingAssignment` meanwhile.
- **Stop handlers must finish within about a third of the session timeout.** Increase the session timeout if they
  need longer.

## Custom client services

The SQL Server / Redis fixes are in the built-in client services; the public `IClientService` interface is unchanged.
A custom `IClientService` passed to a provider keeps the 4.2.1 behavior (no lease guard on coordinator writes; a
recovered follower stays `Terminated`). A custom `IZooKeeperService` keeps its own barrier deletion.

## Tests and documentation

- TLA+ specifications of both protocols, with the configurations that showed each defect and now hold ([
  `docs/tlaplus/README.md`](../tlaplus/README.md)).
- New tests: coordinator lease guard (unit, both backends; real SQL Server and Redis); a follower recovering from a
  store error (real SQL Server and Redis); barrier ownership and the cancellation path (unit; real ZooKeeper); handlers
  stopping while the ensemble is unreachable (real ZooKeeper, `DisconnectionTests`).
- Architecture overview: safety mechanisms for ZooKeeper; README and ZooKeeper README updated.
