# Rebalancer 4.3.2 – release notes

Packages: `Rebalancer.Core`, `Rebalancer.SqlServer`, `Rebalancer.Redis`, `Rebalancer.ZooKeeper`,
`Rebalancer.Extensions.DependencyInjection`, `Rebalancer.Extensions.Diagnostics.HealthChecks` (all 4.3.2).

Change record: [CR-0012](../change-records/CR-0012-release-4-3-2.md). No public API, configuration or data format
change. Two fixes that make the clients behave as documented; both change what hosts observe, so read "What hosts see"
under each.

## Fix: SQL Server and Redis applied OnAssignmentDelay to every heartbeat

[PRB-0007](../problem-records/PRB-0007-assignment-delay-delays-keep-alives.md). Affects SQL Server and Redis hosts that
set `ClientOptions.OnAssignmentDelay`. ZooKeeper was not affected.

The option is documented as a delay before `OnAssignment`. The SQL Server and Redis clients instead waited for it
before every heartbeat tick, and every tick begins with the node's keep-alive. With a delay at or above the group's
keep-alive expiry (the lease expiry), which the option's own documentation suggests for RabbitMQ, the coordinator took
live nodes for dead and the group never settled: on a test group with a 5 s expiry and a 10 s delay, two nodes did not
converge within 90 s. With shorter delays, rebalances and stop requests were slowed by up to one delay.

Now the delay runs once per assignment, from the moment a node sees it until its `OnAssignment` handlers run, as on
ZooKeeper. Keep-alives and stop requests are never delayed. A stop that arrives during the delay cancels the pending
start; a different assignment starts the delay again.

What hosts see:

- `OnAssignment` comes the full delay after the node receives its assignment (before, anywhere between none and the
  full delay), and `GetCurrentState()` reports `PendingAssignment` until then.
- A node's record says `Active` only once its handlers run; a rebalance during the delay does not wait for it.
- **Upgrade every node of a group that sets the delay.** A 4.3.1 node keeps delaying its keep-alives.
- If you lowered the delay below the keep-alive expiry, or raised `LeaseExpirySeconds`, to work around this, you can
  set them back.

## Fix: a stopped client never reported ClientState.Stopped

[PRB-0006](../problem-records/PRB-0006-stopped-client-never-reports-stopped.md). All backends.

After `StopAsync`, a SQL Server or Redis client reported `PendingAssignment` (in 4.3.0 and earlier, its last
assignment as `Assigned`), and a ZooKeeper client reported `NotStarted`, although `ClientState.Stopped` documents
exactly this case. As a result, `BlockAsync` did not return on SQL Server and Redis when the client was stopped by
another caller, and the health check reported a stopped SQL Server or Redis client `Healthy`, then `Degraded`.

Now `GetCurrentState()` and `GetAssignedResources()` report `Stopped` (with no resources) once the client has stopped,
on every backend. A client that gave up after an error still reports `Aborted`.

What hosts see:

- **Code that compared the state after a stop with `NotStarted` (ZooKeeper) or `PendingAssignment` (SQL Server, Redis)
  must compare with `Stopped`.**
- `BlockAsync` returns once the client is stopped, whoever stops it.
- The health check reports a stopped client `Unhealthy`, as ADR-0023 specifies.
- ZooKeeper: `GetAssignedResources()` of a client that gave up now reports `Aborted` with no resources, as
  `GetCurrentState()` already did and as SQL Server and Redis do since 4.2.0 (it reported `PendingAssignment`).

## Custom client services

The OnAssignmentDelay fix is in the coordinator and follower roles, so it applies with a custom `IClientService` too.

## Tests and documentation

- New tests: the state after a stop and `BlockAsync` (unit; real SQL Server, Redis and ZooKeeper); keep-alives during
  the delay, the delay after a grant, its cancellation by a stop or a step-down, and the coordinator's own share (unit);
  two nodes with a delay longer than the keep-alive expiry (real SQL Server and Redis).
- The randomised SQL Server and Redis tests now also check what each node's handlers process, not only what the
  client reports ([US-0024](../user-stories/US-0024-randomised-tests-check-what-nodes-process.md)); they catch the
  defect fixed in 4.3.1, which they missed before.
- The TLA+ specification of the SQL Server / Redis protocol models `OnAssignmentDelay` ([
  `docs/tlaplus/README.md`](../tlaplus/README.md)).
- `ClientOptions.OnAssignmentDelay` documentation describes when the delay runs.
